## 一、流程纪律

#### C44 · warn · CI-1
- **位置**：guardai.yml（allowed_dirs）
- **问题**：新增 `src/GuardAI.AI/Learn/` 模块没有登记进目录白名单，CI structure 检查报 3 处违规（Learn 三个文件"疑似 AI 自由发挥新建了目录"）。
- **根因**：新模块落位的登记动作没进写码流程——设计上这是标准动作（"新增目录补进白名单"），但只在被检查器逮住后才补。
- **修复**：白名单补 `src/GuardAI.AI/Learn/*` 条目（含 purpose 说明）。
- **可沉淀规则** →【提示词规则】新建目录/模块前，先在 guardai.yml 白名单登记再落文件；这是标准流程不是事后补救。

#### C45 · warn · CI-2
- **位置**：推送流程（人/AI 的操作纪律）
- **问题**：learn 功能推送前只跑了单测（236 全绿）没跑 `guardai check`，违规直达 CI 才暴露。
- **根因**：把"测试绿"当成了"可推送"，漏了自家门禁——工具作者反而没走工具的流程。
- **修复**：本轮修复推送前执行 `check --mode all`（0 违规才推），CI 确认绿灯。
- **可沉淀规则** →【提示词规则】提交/推送 guardAI 代码前必须跑 `guardai check` 归零；测试绿 ≠ 可推送，两道闸都要过。

## 二、资产级重复

#### C46 · warn · CI-3
- **位置**：`src/GuardAI.AI/Learn/LearnAdvisor.cs`（对照 `Init/InitAiAdvisor.cs`）
- **问题**：LearnAdvisor 的 `AdviseAsync`/`ParseReply`/`ExtractJson`/`ReadText` 与 InitAiAdvisor 相似度 100%/92%——实现 learn 时照搬了 init 顾问的骨架。
- **根因**：AI 写"同族新模块"（第二个顾问）时的典型行为：复制相似模块改皮。复制的是**骨架**（组提示词→调模型→解析 JSON 的流程），不是业务——业务差异其实只在提示词与 schema。
- **修复**：抽 `LlmReply`（回复解析共用件）+ `AdvisorRunner`（调用流程唯一一份），两顾问只留 BuildPrompt/ParseReply 差异；删复制的包装。
- **可沉淀规则** →【提示词规则】写同族新模块（第 N 个适配器/顾问/客户端）前，先抽公共骨架再写差异部分；"复制相似模块改名"是资产级违规，引擎必逮。→【本地检查】重复检测已覆盖（Jaccard+Containment 双通道）。

## 三、检测器盲区（执法者自己的 bug）

#### C47 · warn · CI-4
- **位置**：`GuardAI.Checks/Assets/CodeSimilarity.cs`（Tokenize）+ `CSharpMemberParser.cs`（Clean）
- **问题**：字符串字面量清洗后全归一为 `str` token——两段**内容完全不同**的提示词方法体被判 100% 重复（`LearnAdvisor.static` vs `InitAiAdvisor.static`，实为两个 BuildPrompt）。
- **根因**：归一化"吸收字面量微调"的原设计把区分信号也吞了。对提示词/SQL/JSON 模板密集的代码，任何两个同类方法必然撞车。
- **修复**：清洗保留内容长度标记（`"N"`），token 增精确 `len_N` + 幂次桶 `lenb_N`——不同文本（长度不同）分开，±几字微调（同桶）仍吸收。
- **可沉淀规则** →【本地检查】（已修）归一化不得吞掉区分信号：吸收"微调"要保留"不同"的判别特征（长度/类型/结构）。

#### C48 · warn · CI-5
- **位置**：`GuardAI.Checks/Assets/CSharpMemberParser.cs`（方法名解析）
- **问题**：返回值是元组的方法（`public static (string System, string User) BuildPrompt(...)`）方法名被解析成 `"static"`——首个 `(` 是元组的，不是参数表。
- **根因**：签名解析按"第一个左括号"截头部，没考虑返回值里的平衡括号组。
- **修复**：参数表左括号按"配对右括号后跟 `=>`/`{`/`;`/`where`/结尾"定位（`FindParamsOpenParen`），逐组跳过前置括号组。
- **可沉淀规则** →【本地检查】（已修）语法解析按**终结符语义**定位结构边界，不按"第一个特征字符"偷懒。

## 四、误报治理

#### C49 · warn · CI-6
- **位置**：`.guard/duplicates-baseline.json`（首跑收编机制）
- **问题**：修复重构后残留的 AdviseAsync 薄委托仍被判重，`detectorVersion` 升级的**首跑收编把这个误报对自动吞进基线**——看似"修好了"，实际是走后门糊豁免。
- **根因**：收编机制的设计对象是"检测能力升级挖出的存量真债"，无法区分真债与误报；误报被收编后会被永久掩盖（同名对再犯也报不出来）。
- **修复**：摘除误收编对 → 真正消根（删重复包装）→ `--strict` 严格审计验证对真消失（strict 连基线内存量都报，是"验证非藏基线"的标准手段）。
- **可沉淀规则** →【AI 审查清单】收编/豁免动作后必须人工抽查收编内容；误报被收编 ≠ 修复完成，必须摘除并修根因。→【提示词规则】逃生口（exclusions/基线）只能消化真存量，不能消化误报。

#### C50 · info · CI-7
- **位置**：`LearnAdvisor.AdviseAsync`（修复过程中的方法论教训）
- **问题**：想靠"给薄委托加边界归一化逻辑"拉开相似度——失败，仍 95% 判重。
- **根因**：Containment（包含度）通道以小 body 为分母——**往大 body 里加内容不降包含度**，小 body 的三元组仍是大 body 的子集。
- **修复**：唯一消根是"流程只留一份"：删两个包装，调用点直连公共 `AdvisorRunner.AdviseAsync`。
- **可沉淀规则** →【AI 审查清单】判重修复方法论：模板型代码（同骨架不同参数）加料没用，要么抽骨架合一，要么改写其中一份的控制流；先判"是模板还是复制"再选修法。
